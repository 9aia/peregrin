# ADR-0034: Type generation from AC field declarations

## Status

Accepted (implemented — see implementation notes inline)

## Context

The AC language lets documents declare their own schema inline via `fields:`.
Each field schema is a key-value fragment with AC-specific properties
(`expr`, `arg`, `merge`, `inheritable`, `mutable`) alongside type vocabulary
(`type`, `required`, `properties`, etc.). The language kernel is seven
primitives that compose to produce emergent patterns (ADR-0033, SPEC
section 14).

Today, IDE intellisense for YAML files is generated by the TypeScript CLI's
`typegen` command (`apps/cli/src/main.ts:427`). That implementation is
workflow-specific — it hardcodes the agent-campaign structure (`nodes`,
`events`, `snippets`, `handlers`) and does not understand AC language
`fields:` declarations. It cannot generate schemas for self-describing AC
documents.

The AC language already has a pattern for schema-system decoupling:

```
ac-schema      — abstract Schema<V> trait (zero deps)
ac-schema-json — JSON Schema implementation of Schema<V>
```

The same pattern should apply to type generation. The typegen core should
not know about JSON Schema, TypeScript, or any specific output format.

`extract_fields` already produces `Vec<(String, JsonValue)>` — field name +
raw schema pairs. These are `JsonValue` fragments — a serialization format,
not a schema system. The vocabulary they use (`type`, `required`, etc.)
overlaps with JSON Schema by convention, but the typegen core does not
assume any particular schema vocabulary.

### Requirements

- Generate type definitions from any AC document with `fields:`.
- Strip AC-specific keys (`expr`, `arg`, `merge`, `inheritable`, `mutable`)
  so the output is clean schema data with no AC residue.
- Exclude `merge: true` fields from the output — they are removed from data
  after computation, so they should not appear as properties.
- **Resolve imports at the type level** — for merge fields with
  `expr: "import('...')"` (static path) or `expr: "import(arg)"` (path
  from data), follow the import path, extract the imported document's
  `fields:`, generate its schema, and merge the imported field schemas
  into the parent. This mirrors the runtime merge: just as `merge: true`
  spreads imported data into the parent at runtime, the typegen spreads
  imported schemas into the parent schema at generation time.
- **Follow data values for import paths** — when a merge field uses
  `expr: "import(arg)"` with `arg: { type: string }`, the typegen reads
  the field's data value (e.g. `import: "./base.yml"`) to resolve the
  import path. This is static analysis of the data, not expression
  evaluation.
- Emit generated files and inject IDE hint comments (`# yaml-language-server:
  $schema=` for JSON Schema) into source files.
- **Be schema-system-agnostic**: the core typegen crate must not depend on
  any specific schema system. JSON Schema is the first backend; TypeScript
  `.d.ts`, Rust structs, or Python `TypedDict` could follow without
  changing the core.
- Be emergent: the generator should not need to understand the `import`
  field pattern or other emergent patterns. It operates on the extracted
  field schemas, strips AC keys, and emits. The schema reflects the final
  data shape after the pipeline.

### Type-level merge resolution

The runtime pipeline merges data: `merge: true` fields are spread into the
parent and removed. The typegen must mirror this at the type level:

1. **Detect merge fields** — fields with `merge: true` in the schema.
2. **Detect import paths** — for each merge field, check if `expr:` contains
   `import('...')` (static) or `import(arg)` (data-driven). For
   data-driven imports, read the field's data value from the document.
3. **Follow imports** — load the imported document, extract its `fields:`,
   and recursively generate its schema.
4. **Merge schemas** — spread the imported document's field schemas into the
   parent's schema. Parent wins on conflicts (same as runtime merge).
5. **Exclude merge field** — remove the merge field itself from the parent
   schema (same as runtime merge).

This means the generated schema for:
```yaml
fields:
  import:
    type: object
    arg: { type: string }
    expr: "import(arg)"
    merge: true
  host: { type: string }
  port: { type: number }
import: "./base.yml"
```

Produces a schema with `host` and `port` as properties — the `import` field
is gone, and any fields from `base.yml` that aren't already in the parent
are merged in. The typegen mirrors the runtime pipeline's final data shape.

### Constraints

- Must work offline (no network calls, all imports are local files).
- Must be fast — generation is a build-time step, not runtime.
- Must be deterministic — same input always produces same output.
- Must integrate into the existing `ac` CLI as a subcommand.

## Decision

Create a three-layer architecture: a schema-agnostic core crate, a
special-key handler crate, and format-specific backend crates. This
mirrors the existing `ac-schema` / `ac-schema-json` split, with an
additional layer for AC-specific key handling.

### Layer 1: Core (`ac-typegen-core`)

The core crate is schema-system-agnostic. It depends only on `serde_json`
(for `JsonValue` as the data carrier) and `indexmap`. It has zero
knowledge of any AC-specific key (`expr`, `arg`, `merge`, `inheritable`,
`mutable`). It does **not** depend on `ac-schema`, `ac-schema-json`, or
any schema validation crate.

The core provides generic primitives:

- `TypegenContext` — holds field name → schema fragment pairs in an
  `IndexMap` (preserves insertion order, O(1) lookups).
- `strip_keys_in_place` — recursively removes given keys from JSON values.
- `TypegenBackend` trait — format-specific output generation.

The core does **not** know which keys are AC-specific. The orchestrator
(CLI, compiler pass) composes the core with the key handler crate and
import resolver to produce clean schema fragments.

```rust
/// Schema-system-agnostic generation context.
/// Built from raw field schemas. AC-key crates filter and strip the
/// context. Import resolution merges imported schemas. Backends consume
/// the final clean fragments.
pub struct TypegenContext {
    /// Field name → schema fragment.
    pub fields: IndexMap<String, JsonValue>,
}

impl TypegenContext {
    /// Build from raw field schemas. No filtering, no stripping.
    pub fn from_schemas(schemas: &[(String, JsonValue)]) -> Self { ... }
    /// Remove fields by name (used by merge key handler).
    pub fn remove_fields(&mut self, names: &[String]) { ... }
    /// Recursively strip given keys from all field schemas.
    pub fn strip_keys(&mut self, keys: &[&str]) { ... }
    /// Merge additional fields in (parent wins). Used by import resolver.
    pub fn merge_fields(&mut self, imported: &[(String, JsonValue)]) { ... }
}

/// A type definition generator. Format-specific.
///
/// The core produces clean `JsonValue` fragments. Each backend interprets
/// them and produces its target format.
///
/// - `ac-typegen-backend-json-schema` → JSON Schema (`JsonValue`)
/// - Future: `ac-typegen-typescript` → TypeScript `.d.ts` (string)
/// - Future: Rust structs, Python TypedDict, etc.
pub trait TypegenBackend: Send + Sync {
    type Output;
    fn generate(&self, ctx: &TypegenContext) -> Self::Output;
    fn extension(&self) -> &str;
    fn ide_hint(&self, schema_rel_path: &str) -> String;
}
```

### Layer 2: Special key handler (`ac-typegen-key-set-special`)

This crate knows the 5 special AC keys (`arg`, `expr`, `inheritable`,
`merge`, `mutable`). Each key has its own module with a `KEY` constant
and a `strip_key` function that delegates to `TypegenContext::strip_keys`.
Keys with additional behavior (`expr`, `merge`, `arg`) also expose helper
functions.

Key names are resolved via the `DocumentVocabulary` trait from
`ac-dialect`, not hardcoded. A custom dialect with different key names
(e.g. `expr` → `compute`) works without changes to this crate.

Depends on `ac-typegen-core` for generic primitives and `ac-dialect` for
the vocabulary trait.

### Layer 2b: Import resolver (`ac-typegen-import`)

Follows `import()` expressions in merge fields, resolves them via a
`ModuleResolver` trait (from `ac-resolver-core`), and merges imported
schemas into the parent context. I/O is delegated to the resolver
implementation — file, virtual, HTTP, or git.

Depends on `ac-typegen-core` and `ac-typegen-key-set-special` (for
filtering merge fields and reading `expr` values).

### Layer 3: Backends

Each backend crate implements `TypegenBackend`. Backends depend on
`ac-typegen-core` but not on each other.

#### `ac-typegen-backend-json-schema` — JSON Schema backend

`JsonSchemaBackend` implements `TypegenBackend<Output = JsonValue>`:

1. **Compose** — build a root JSON Schema from the clean fragments:
   ```json
   {
     "$schema": "http://json-schema.org/draft-07/schema#",
     "type": "object",
     "properties": { ... },
     "additionalProperties": false
   }
   ```
2. **Resolve imports** — for fields with static import paths, generate
   `$ref` to the imported file's schema path. The imported file gets its
   own schema generated recursively.
3. **Emit** — write `.schema.json` files and inject
   `# yaml-language-server: $schema=<path>` comments.

The JSON Schema backend is a near-passthrough: the clean fragments already
use JSON Schema vocabulary (`type`, `required`, `properties`, etc.), so
the backend wraps them in a root schema envelope and handles cross-references.

#### Future: `ac-typegen-typescript`

A TypeScript backend would interpret the same clean fragments differently:
`{ type: "string" }` → `string`, `{ type: "object", properties: {...} }`
→ `interface`, etc. The core's clean fragments are the input; the
TypeScript backend produces `.d.ts` output. No changes to the core needed.

### Why three layers, not one

A single crate that "also supports other formats" tends to accumulate
format-specific assumptions in the core. The layer split enforces
boundaries:

- The core **cannot** import `ac-schema-json` or any format-specific crate.
- The core **cannot** know which keys are AC-specific — it only provides
  generic `strip_keys` and `remove_fields` primitives.
- The key handler **cannot** produce format-specific output — it only
  filters and strips.
- Backends **must** consume the clean fragments and interpret them.

This is the same principle as `ac-schema` (trait, zero deps) vs
`ac-schema-json` (impl, depends on trait). The trait crate defines the
abstraction; the impl crate provides the concrete behavior.

The key handler layer exists because the set of special keys is an
AC-language concern, not a core-primitive concern. Separating it lets
the core remain reusable for non-AC type generation, and lets custom
dialects provide their own key handler crates if they introduce keys
beyond the standard five.

### Why strip, not transform

AC field schemas use schema vocabulary by convention (`type`, `required`,
`properties`). The key handler strips AC-specific keys and passes through
everything else unchanged. This means:

- Any schema vocabulary keyword in a field declaration is preserved.
- The key handler does not interpret schema vocabulary — it only knows
  which keys are AC-specific (via `DocumentVocabulary`).
- Future schema vocabulary additions work without core or key handler
  changes.
- Each backend interprets the vocabulary it understands.

### Why merge fields are excluded but their imports are resolved

After the pipeline runs (`extract → interpolate → compute → merge →
validate`), merge fields are spread into the parent and removed from data.
The generated types must reflect the final data shape, not the
intermediate one. A merge field like `_base` with `{ type: object,
merge: true, expr: "import('./base.yml')" }` should not appear as a
property — its contents are flattened into the parent.

But unlike a simple merge field with a literal object value, a merge field
with `expr: "import(...)"` pulls fields from an external document. The
typegen must follow that import and merge the imported schemas into the
parent, just as the runtime merges the imported data. The merge field
itself is excluded; the imported schemas are spread in.

### Emergent behavior

The `import` field pattern (`arg: { type: string }` + `expr: "import(arg)"`
+ `merge: true`) is fully resolved by the typegen:

1. The field is a merge field → excluded from the output schema.
2. The `expr` is `import(arg)` → the typegen reads the data value
   (e.g. `import: "./base.yml"`) to get the path.
3. The imported document is loaded, its `fields:` are extracted and
   stripped, and its schemas are merged into the parent.
4. The result is a schema that includes both the parent's declared
   fields and the imported document's fields — exactly mirroring
   what the runtime pipeline produces.

The generator does not need to understand this as a pattern. It performs
three generic operations — filter merge fields, detect imports, merge
schemas — and the `import` field pattern emerges as their composition.
The same three operations handle `expr: "import('./static.yml')"` (static
path) and `expr: "import(arg)"` (data-driven path) uniformly.

### Crate structure

```
crates/typegen-core/                  — generic primitives (no AC key knowledge)
  src/
    lib.rs                            — strip_keys_in_place, module docs
    context.rs                        — TypegenContext (from_schemas, remove_fields, strip_keys, merge_fields)
    backend.rs                        — TypegenBackend trait
    lib_tests.rs

crates/typegen-key-set-special/       — knows the 5 special AC keys
  src/
    lib.rs                            — module docs, re-exports
    arg.rs                            — arg key: has_arg(), strip_key()
    expr.rs                           — expr key: get_expr(), strip_key()
    inheritable.rs                    — inheritable key: strip_key()
    merge.rs                          — merge key: is_merge_field(), filter_fields(), strip_key()
    mutable.rs                        — mutable key: strip_key()
    *_tests.rs                        — per-key tests

crates/typegen-import/                — import resolution (via ModuleResolver)
  src/
    lib.rs                            — apply_imports()
    import_detect.rs                  — detect static and data-driven import() paths
    import_resolve.rs                 — follow imports, extract + strip + merge schemas
    *_tests.rs

crates/typegen-backend-json-schema/   — JSON Schema backend
  src/
    lib.rs                            — JsonSchemaBackend, implements TypegenBackend
    compose.rs                        — build root JSON Schema from clean fragments
    emit.rs                           — write .schema.json, inject yaml-language-server
    *_tests.rs
```

The orchestrator (compiler pass or CLI) composes them in order:

```rust
// 1. Core: build context from raw schemas
let mut ctx = TypegenContext::from_schemas(&extracted.schemas);

// 2. Key handler: filter + strip (pure)
ac_typegen_key_set_special::merge::filter_fields(&mut ctx, &extracted.merge);
ctx.strip_keys(&ac_keys);

// 3. Import resolution: follow imports, merge (via resolver)
ac_typegen_import::apply_imports(&mut ctx, &extracted, &data, &resolver, &vocab);

// 4. Backend: generate output (pure)
let schema = backend.generate(&ctx);
```

### CLI integration

Add a `typegen` subcommand to `ac-cli`:

```
ac typegen --input main.yml [--stdout] [--output-dir .ac/generated/schemas]
        [--format json-schema]   (default; future: typescript, rust)
```

The CLI selects the backend based on `--format`. The core extracts and
strips; the backend generates and emits.

This replaces the TypeScript `typegen` command for AC language documents.
The TypeScript `typegen` remains for workflow-specific schema generation
(nodes, events, handlers) until the workflow engine migrates to AC
language `fields:` declarations.

### Workspace changes

- Add `crates/typegen-core`, `crates/typegen-key-set-special`,
  `crates/typegen-import`, and `crates/typegen-backend-json-schema` to
  the workspace `Cargo.toml`.
- `ac-typegen-core` depends on `serde_json` and `indexmap`.
- `ac-typegen-key-set-special` depends on `ac-typegen-core`,
  `ac-dialect`, and `serde_json`.
- `ac-typegen-import` depends on `ac-typegen-core`,
  `ac-typegen-key-set-special`, `ac-dialect`, and `ac-resolver-core`.
- `ac-typegen-backend-json-schema` depends on `ac-typegen-core`,
  `serde_json`, and `indexmap`.
- `ac-compiler-pass-resolve` depends on `ac-typegen-core`,
  `ac-typegen-key-set-special`, and `ac-typegen-import`.

## Consequences

### Positive

- **IDE intellisense for any AC document** — any file with `fields:` gets
  a JSON Schema that IDEs can use for autocomplete, validation, and hover
  tooltips.
- **Type-level merge resolution** — the generated schema mirrors the
  runtime pipeline's final data shape. Merge fields are excluded, their
  imported schemas are spread in, and parent wins on conflicts. The IDE
  sees exactly the fields the runtime produces — no more, no less.
- **Schema-system decoupled** — the core knows nothing about JSON Schema
  or AC keys. Adding a TypeScript or Rust backend requires implementing
  `TypegenBackend`, not modifying the core. This mirrors the
  `ac-schema` / `ac-schema-json` pattern already established in the
  codebase.
- **Key names are pluggable** — the key handler resolves key names via
  the `DocumentVocabulary` trait, so custom dialects with different key
  names work without code changes.
- **Zero knowledge of output format needed** — the key handler strips AC
  keys and passes through everything else. Each backend interprets the
  vocabulary it understands.
- **Emergent** — the generator works with the `import` field pattern,
  `config` field pattern, and any future emergent pattern without code
  changes. It operates on the extracted schema, not the pattern.
- **Replaces ad-hoc typegen** — the TypeScript `typegen` command's
  schema-generation logic can eventually be replaced by this crate,
  unifying schema generation in one place.

### Negative

- **Four crates instead of one** — the core/key-handler/import/backend
  split adds crate boundaries. This is intentional and mirrors the
  existing `ac-schema` / `ac-schema-json` pattern, with an additional
  layer for AC-specific key handling and import resolution.
- **JSON Schema is verbose** — the generated schemas are larger than
  hand-written ones. This is acceptable for machine-generated files.
- **Static analysis only** — the core cannot evaluate `import()` with
  dynamic paths (e.g., `import(concat(env.ENV, '.yml'))`). Static import
  paths in `expr: "import('...')"` are detected; dynamic imports are
  left as generic `{ type: object }`.
- **Two typegen commands temporarily** — the TypeScript CLI's `typegen`
  and the Rust CLI's `typegen` coexist until migration. The TypeScript
  command handles workflow structure; the Rust command handles AC
  language field schemas.

### Neutral

- Generated files go to `.ac/generated/schemas/` — same convention as
  the TypeScript typegen. This directory should be in `.gitignore`.
- The IDE hint comment (e.g. `# yaml-language-server: $schema=` for JSON
  Schema) is injected at the top of source files. This is a write to user
  files — the CLI should only inject if the comment is not already present.
  The comment format is backend-specific (`ide_hint()` on `TypegenBackend`).
