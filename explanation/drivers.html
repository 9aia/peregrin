Drivers ​

Drivers execute node logic. A node declares driver: <name>, and the runner looks the name up in its registry at fire time. The driver receives the node, the trigger events, and the execution context — it runs the action and returns the events to publish.

rust
pub trait Driver: Send + Sync {
    fn name(&self) -> &str;
    fn input(&self) -> Option<EventSchema> { None }
    fn output(&self) -> &[EventSchema] { &[] }
    fn invoke(
        &self,
        node: &Node,
        triggers: &[Event],
        ctx: &ExecutionContext,
    ) -> Result<Vec<Event>, DriverError>;
}

input is the contract params validates against (when the node doesn't declare its own input:); output holds per-emitted-type payload contracts. The runner validates resolved params and emitted payloads against them before events reach the bus.

The unified registry ​

peregrin_engine::Registry is one flat map of names to drivers — there is no separate kind of registry for triggers, actions, or sinks (ADR-0082 §4). An ingress driver is just a driver that emits asynchronously for the life of the run instead of returning its events; a sink is just a driver whose node fires on terminal campaign events and publishes the verdict out.

Resolution is exact match first, then :-prefix — driver: agent:claude resolves the driver registered under agent, and the suffix is the driver's own to interpret.

rust
let registry = Registry::default()
    .with("shell", Arc::new(ShellDriver::new()))
    .with("my-driver", Arc::new(MyDriver));

Two ingress drivers exist as crates — github-webhook (HMAC-verified push listener) and sturn-poll (git-ref WAL poller) — and compose the same way once the node's per-run wiring hands them the run's Injector. The v1 python/cli/stdin/generic webhook/ streaming drivers and the litellm/apprise plugin drivers are not ported.

What a driver gets — ExecutionContext ​

Beyond the node and triggers, ctx carries the shared run state: config, the fire's resolved params, secrets (the run's secrets record), state (scoped when state.key is set), capabilities, fires, idempotency_key, traceparent, dry_run, and the strict missing_secrets audit ledger.

Four side channels shape the graph:

  • ctx.emit(event) — queue extra events; they publish after the node's own returned events.
  • ctx.inject(specs) — add nodes mid-run (the runner driver reads them from the trigger payload).
  • ctx.schedule_at(event, at) / schedule_in(event, dur) — defer an emission onto the runner's timer heap; the event publishes when the deadline lands and holds the run open until then (ADR-0018).
  • ctx.run_sub(campaign, opts) — run a nested campaign on a fresh, isolated Runner (own bus/log/state; the subworkflow driver's channel, ADR-0022).
  • ctx.request_shutdown() — cancel the run after the current batch.

Drivers also template-resolve their own params a second time inside invoke (against the bound trigger) — the ${event.*}/${config.*} forms a param can carry are specified in Scope resolution.

Secret names, never secret values ​

Drivers that need credentials take a *_env param naming a secret key — token_env, secret_env, ssh_env — resolved through the capabilities.secrets gate and ctx.get_secret. Values never sit in params or config; the run's secrets record is the only source. See Safety.
